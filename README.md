# GameAnalytics

Дипломный проект группы SE-2431: кросс-игровая аналитическая платформа для CS2 и Dota 2 с обнаружением ошибок на основе ИИ.

## Проблема и целевые пользователи

Игрокам CS2 и Dota 2 нужен единый способ смотреть доступную статистику и разбирать конкретные эпизоды своих матчей. Сводные показатели помогают оценить результат, но сами по себе не объясняют причины неудачных действий. GameAnalytics объединяет игровой профиль, историю матчей и персональный анализ записи с привязкой выводов к событиям.

Целевые пользователи: игроки, тренеры и аналитики любительских и полупрофессиональных команд, киберспортивные клубы и вузовские лиги.

## Ожидаемые результаты и границы проекта

Целевой MVP включает:

- Публичный просмотр доступной базовой статистики игроков CS2 и Dota 2, единый профиль и историю матчей.
- Подтверждение своего Steam-аккаунта и ручную загрузку записи из карточки собственного матча.
- Проверку соответствия записи матчу, асинхронную обработку и приватный отчёт с эпизодами потенциальных ошибок, временем и объясняющими признаками.
- Пять прикладных сервисов: Users / Profiles, Matches / Uploads, Data Processing, Statistics и Mistake Analysis.
- Free: три успешных анализа за календарный месяц UTC; демонстрационный Premium без месячного лимита. Один активный анализ на пользователя; исходные записи хранятся 30 суток.
- Документированные API, воспроизводимое развёртывание и оценку обнаружения ошибок относительно baseline на размеченных эпизодах.

CS2 охватывает FACEIT и Premier; для Dota 2 предусмотрена интеграция с OpenDota. Автоматическое скачивание демок, реальные платежи, античит и расширенные командные функции не входят в MVP. Полная история любого игрока не гарантируется: интерфейс должен явно показывать недоступность данных. Подробности: [ТЗ](docs/requirements/mvp.md).

## Текущий статус

Этап проектирования и исследований: подготовлены требования, архитектурные схемы, сравнения, план проверок и кликабельный HTML-прототип на вымышленных данных. Есть примеры ответов внешних API и исследование разбора демок. Серверная платформа, ML-модели и Kubernetes-развёртывание ещё не реализованы; практическая проверка Premier вынесена в GA-58. Точность будущего анализа пока не измерена.

| Область | Технологии |

| Текущий UI-прототип | HTML, CSS, JavaScript; стек полноценного frontend уточняется |

## Конфигурация и запуск

Настоящие пароли, токены, ключи API и файлы `.env` не добавляются в репозиторий. Для локальной настройки используется файл `.env.example`.

### Запуск прототипа

1. Клонировать репозиторий или скачать ZIP выбранной версии и распаковать его.
2. Открыть `docs/prototype/index.html` в современном браузере. Установка зависимостей, API-ключи и backend не нужны.
3. Проверить поиск и чужой профиль, историю и карточку своего матча, выбор тестовой демки, обработку и отчёт. Переключатель «Демо-сценарий» показывает дополнительные состояния.

### Проверка прототипа

В карточке матча доступны тестовые файлы: `match_ok.dem`, `other_match.dem`, `not_my_account.dem`, `broken.dem`. Проверить успешный анализ, несовпадение матча, чужой аккаунт и ошибку обработки. Во время обработки второй анализ блокируется; попытка списывается после успеха и освобождается при ошибке. Это имитация, реальные демки не отправляются на сервер. Полный перечень сценариев: [README прототипа](docs/prototype/README.md).

### Воспроизведение схем

При установленном Node.js выполнить из корня репозитория:

```sh
node docs/architecture/diagrams/render.mjs
```

Генератор не требует сторонних пакетов и обновляет SVG в `docs/architecture/diagrams/`.

### Серверная платформа и тесты

Запуск backend пока не реализован; готовой команды запуска всего приложения и автоматического набора тестов нет. Инструкции установки, запуска сервисов и выполнения тестов будут добавляться вместе с исполняемым кодом. Сейчас методика и критерии будущих проверок описаны в [плане тестирования](docs/testing/ga-52-test-plan.md).

## Правила работы

1. Для каждой задачи создаётся отдельная ветка от актуального `main` с ID задачи в названии.
2. Коммиты содержат ID задачи, например: `GA-57: Add repository structure`.
3. Изменения отправляются через Pull Request в `main`.
4. Pull Request проверяет другой участник команды.
5. После одобрения PR сливается в `main`, а задача закрывается в YouTrack после выполнения её критериев.
