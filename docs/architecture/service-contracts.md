## Пять сервисов и владение данными

| № | Сервис / владелец | Данные и обязанности | Вне ответственности |
|---|---|---|---|
| 1 | Users/Profiles — Амир | Сессии, проверенный SteamID, профиль, тариф, версия прав; единственный владелец этих таблиц | Задания, баланс использованных анализов |
| 2 | Matches/Uploads — Амир | Адаптеры FACEIT/OpenDota/Premier, карточки, uploads, jobs, quota ledger, outbox; координатор конвейера | Разбор бинарных файлов и ML |
| 3 | Data Processing — Ерхан | Проверка сигнатуры/размеров, распаковка, состав и идентичность матча, нормализованный набор событий, версия парсера | Решение о тарифе и выдача личного отчёта |
| 4 | Statistics — Амир | Публичные агрегаты с источником, выборкой и версией; отдельная read model | Приватные рекомендации и исходные файлы |
| 5 | Mistake Analysis — Қажмұрат | Baseline/ML, объяснимые эпизоды, версия модели, приватный отчёт | Авторизация загрузки, квота и импорт истории |

Frontend — Қажмұрат. Gateway выполняет маршрутизацию, JWT-проверку и rate limit; не владеет бизнес-данными и не считается шестым сервисом. Уведомление о статусе — чтение задания через polling, отдельного сервиса уведомлений в MVP нет. Workers и адаптеры — компоненты пяти сервисов.

PostgreSQL разделён логически: своя схема/роль у каждого владельца; миграции сервиса не меняют чужие таблицы. Даже при одном экземпляре запрещены прямые межсервисные SQL-записи и JOIN. Только API/события. Redis хранит кэш и rate limit; потеря кэша не меняет квоту. Kafka — метаданные событий, S3 — крупные файлы. Амир разворачивает Kafka/S3, Ерхан — кластер, CI/CD и наблюдаемость.

## Границы доверия

1. Браузер недоверенный: `user_id`, SteamID, тариф, размер и checksum от клиента не являются доказательством. Сервер проверяет Steam login, подпись/срок/audience JWT, владение карточкой и доступ к каждому объекту.
2. Публичный вход только через HTTPS gateway. Пользовательские JWT не заменяют сервисную аутентификацию. PostgreSQL, Redis, Kafka, S3 и gRPC закрыты от прямого публичного доступа; отдельные роли и минимальные права. Секреты внешних API не попадают в браузер, репозиторий и логи.
3. Файл — враждебный ввод. Worker без привилегий, с лимитами CPU/RAM/выходного размера/времени и временным каталогом; сеть ограничена необходимыми сервисами. Парсинг не исполняется в HTTP-handler.
4. Внешние API недоверенные и могут не отвечать: валидация схем, timeout, backoff, отдельный статус источника. URL скачивания из произвольного пользовательского ввода не принимаем. Автоскачивания демки в MVP нет.
5. S3 приватен. Для MVP поток загрузки идёт через Matches/Uploads, который считает байты; секрет S3 не выдаётся клиенту. Получение исходника тоже через проверку владельца и `expires_at`. Прямая публичная ссылка на объект недопустима.

## Идентификаторы и модель

Внутренние `match_id`, `job_id`, `upload_id`, `user_id` — UUID-строки. Внешний ID хранится строкой отдельно: уникальный ключ `(source, game, external_match_id)`. SteamID64 всегда строка, без округления JavaScript Number. `game` = `cs2 | dota2`; `source` = `faceit | premier | opendota`. Времена UTC RFC 3339. Отсутствующая статистика — `null`, не ноль. Кросс-игровой профиль объединяет ссылки и периоды; не вводит недоказанный общий рейтинг.

Карточка содержит внешний ID, игру, источник, состав, карту (если применимо), время и версию данных. Снимок карточки фиксируется в задании, чтобы изменение импорта не меняло условия уже идущей проверки. SHA-256 дедуплицирует байты, но не доказывает идентичность матча. CS2: одинаковые карта и состав недостаточны; неоднозначность отклоняется без расхода квоты до проверки метода GA-21. Dota 2: точный match_id плюс владелец в составе. Это риск реализации, не блокер готовности проектного ТЗ.

## Внешний REST-контракт v1

| Метод / путь | Доступ | Ответ / назначение | FR |
|---|---|---|---|
| `GET /v1/players/{steam_id}` | Гость | Профиль и отдельные игровые блоки; `availability`, `updated_at` | 01–02 |
| `GET /v1/players/{steam_id}/matches?cursor=...` | Гость | Карточки, `next_cursor`, состояние каждого источника | 03 |
| `GET /v1/matches/{match_id}` | Гость | Карточка и публичная статистика | 03,09 |
| `GET /v1/auth/steam/start`, `/callback` | Браузер | Серверная проверка Steam-ответа и сессия; не доверять введённому ID | 04 |
| `GET /v1/me/entitlements` | Владелец | Тариф, период UTC, `used`, `reserved`, `limit` (`null` для Premium) | 11 |
| `POST /v1/matches/{match_id}/uploads` | Владелец | Создать upload и одну активную операцию, `201`, идентификатор | 05 |
| `PUT /v1/uploads/{upload_id}/content` | Владелец | Поток файла, `200` после завершения; размер проверяет сервер | 05–06 |
| `POST /v1/uploads/{upload_id}/analysis` | Владелец | Идемпотентный запуск, `202` и `job_id`; повтор возвращает тот же job | 07–08,11 |
| `GET /v1/jobs/{job_id}` | Владелец | Состояние, безопасный код ошибки, `retryable`, ссылка на отчёт после успеха | 07 |
| `GET /v1/reports/{report_id}` | Владелец | Эпизоды и версии; пустой список допустим | 10,12 |
| `GET /v1/uploads/{upload_id}/content` | Владелец | Исходник до `expires_at`, иначе `410` | 12–13 |

Общего `POST /matches` для загрузки произвольного матча нет. Получение отчёта gateway направляет в Analysis с проверяемой идентичностью пользователя; Analysis проверяет владельца отчёта самостоятельно. Premier-подключение с кодами — будущий защищённый адаптер внутри Matches, не обещанный рабочий endpoint этой версии. Публичная выдача не гарантирует историю любого SteamID.

Для изменяющих POST обязателен `Idempotency-Key`: ключ связывается с владельцем, операцией и хешем параметров; повтор с другим телом → `409 IDEMPOTENCY_CONFLICT`. Повтор не порождает новое списание. Ошибка: `{ "error": { "code": "MATCH_UNCONFIRMED", "message": "Соответствие матчу не подтверждено", "retryable": false }, "correlation_id": "uuid" }`. Основные статусы: 400 ввод; 401 нет сессии; 403 нет права; 404 недоступный ресурс; 409 активное задание/исчерпана квота/конфликт; 413 превышен размер; 422 повреждение/несоответствие; 429 rate limit; 503 временно недоступен источник. При чужом приватном ID выдавать 404, не раскрывая существование файла.

## Внутренние синхронные контракты

Go ↔ Go/Python: версионированные protobuf packages `gameanalytics.<service>.v1`, deadline и `correlation_id`, сервисные credentials. Первый набор: `Users.GetEntitlements(user_id)` возвращает tier/version/confirmedSteamID; `Matches.GetJob(job_id)` и `Statistics.GetPlayerStats(steam_id, game)` возвращают только данные своего владельца. Python реализует только нужные ему интерфейсы; основной ML-конвейер получает события Kafka. До реализации команды согласуют `.proto` и OpenAPI в отдельном PR; этот документ не выдаётся за сгенерированную спецификацию.

## События v1

Общий envelope ниже — иллюстративный, не реальные идентификаторы. `match_id` — внутренний ID. `event_id` уникален и сохраняется при повторной отправке; `correlation_id` связывает всю операцию; `causation_id` указывает входное событие либо null для пользовательского запуска.

```json
{
  "event_id": "00000000-0000-4000-8000-000000000001",
  "event_type": "analysis.requested",
  "schema_version": 1,
  "occurred_at": "2026-10-22T00:00:00Z",
  "producer": "matches",
  "correlation_id": "00000000-0000-4000-8000-000000000002",
  "causation_id": null,
  "match_id": "00000000-0000-4000-8000-000000000003",
  "job_id": "00000000-0000-4000-8000-000000000004",
  "payload": { "upload_id": "00000000-0000-4000-8000-000000000005", "object_key": "raw/example", "sha256": "example-only", "card_version": 1, "analysis_version": "baseline-v1" }
}
```

| Событие / topic | Producer → consumers | Обязательные поля payload |
|---|---|---|
| `analysis.requested` / `ga.analysis.requested.v1` | Matches → Processing | upload_id, приватный object_key, sha256, size_bytes, expires_at, game/source/external_match_id, owner_steam_id, снимок/версия карточки, analysis_version |
| `demo.validated` / `ga.demo.validated.v1` | Processing → Matches | validation_version, match_evidence, parser_version |
| `demo.parsed` / `ga.demo.parsed.v1` | Processing → Statistics, Analysis, Matches | dataset_key, dataset_sha256, dataset_schema_version, parser_version, validation_version, game |
| `analysis.completed` / `ga.analysis.completed.v1` | Analysis → Matches | report_id, model_version, report_schema_version, episode_count |
| `analysis.failed` / `ga.analysis.failed.v1` | Processing или Analysis → Matches | stage, code, safe_message, retryable=false; окончательная ошибка |

`demo.parsed` публикуется только после успешной идентификации. У Statistics и Analysis разные consumer groups. Для конвейера ключ partition = `job_id`; импорт/публичные обновления матчей имеют отдельный ключ `match_id`. Между разными topics глобального порядка нет: Matches проверяет допустимый переход и версию job. Старое/повторное событие не откатывает terminal-state. Добавочные необязательные поля совместимы; изменение смысла/удаление обязательного поля — новая major-version topic и периода миграции. Неизвестную major-version consumer помещает в карантин, а не пытается угадать формат.

## Надёжность, ошибки и квота

1. `uploading → uploaded → validating → queued → parsing → analyzing → succeeded`; ошибки ведут в `failed`. После валидации `queued` означает очередь полного парсинга. Полный разбор начинается только при подтверждённом соответствии. Приём upload занимает единственный активный слот пользователя; незавершённая загрузка освобождается по timeout.
2. При запуске Matches в одной PostgreSQL-транзакции блокирует строку квоты/пользователя, проверяет активное задание, резервирует Free-попытку и пишет job + outbox. Индекс/ограничение обеспечивает максимум одного незавершённого задания на пользователя. Premium имеет тот же слот, без месячного лимита.
3. `succeeded` и финальное списание выполняются одной транзакцией только после сохранённого отчёта. `failed` освобождает резерв. Резерв принадлежит календарному UTC-месяцу запуска, даже если работа завершилась в следующем. Free: `used + reserved < 3`; остаток не переносится. Уже готовый результат той же версии возвращается без новой попытки.
4. Outbox публикуется с повторами. Consumer inbox с unique event_id и уникальный ключ `(job_id, analysis_version)` предотвращают двойную бизнес-обработку. Смещение Kafka подтверждается после durable-результата. Промежуточный S3-объект получает детерминированный ключ и checksum; сбой между S3 и БД обрабатывается повтором/очисткой orphan, общей транзакции S3+PostgreSQL нет.
5. Временные ошибки: до 3 повторов после первого запуска с задержками 5/30/120 секунд и jitter, в рамках deadline задания. Эти значения стартовые и подлежат проверке. Несоответствие, неподдерживаемый формат, превышение лимита не повторяются автоматически. После исчерпания повторов событие ошибки отправляется через outbox; проблемное сообщение — в DLQ с причиной, без секретов/файла.
6. Watchdog Matches завершает просроченные задания и возвращает резерв при зависшем worker. Fencing/version check не позволяет позднему worker списать квоту или заменить уже завершённый результат. Операторский replay использует тот же job/event identity; новое пользовательское исследование другой версии — новое явное задание.

## Хранение и критерии реализации

Исходник — 30 суток после успешной загрузки; доступ прекращается в `expires_at`, физическая очистка в пределах 24 часов. Временные/ошибочные объекты удаляются за 24 часа. Промежуточный набор не публикуется: Processing хранит lease до подтверждения чтения обоими потребителями (Statistics и Analysis); успешный ML не разрешает удалить данные ещё не завершившейся статистики. Зависшие leases имеют ограниченный срок и reconciliation; отсутствие набора при replay требует повторного парсинга доступного исходника, а не молчаливого пропуска. Точный срок lease согласуется с deadline полного конвейера при реализации. Отчёт и агрегаты сохраняются отдельно. Срок хранения Kafka не используется как архив исходников.

Лимиты из GA-1 предварительные: вход 1 GiB, распаковка 2 GiB, память worker 2 GiB, парсинг 15 минут. Замеры GA-3 не доказывают эти пределы на полном конвейере. Необходимы испытания таймаутов, OOM, сети, дубликатов и гонок; готовая система здесь не заявлена.

| Проверка | Ожидаемый результат |
|---|---|
| Два параллельных запуска Free | Одно задание/резерв, второе получает конфликт |
| Повтор completed + перезапуск consumer | Один отчёт и одно списание |
| Неверная/неоднозначная CS2-демка | Отказ, резерв освобождён, ML не запускается |
| Переход месяца при обработке | Резерв/списание относятся к месяцу запуска |
| Ошибка ML / зависший worker | Ограниченный retry, затем terminal failure и освобождение квоты |
| Чужой report_id / истёкший файл | Нет доступа, публичный профиль не раскрывает приватные данные |
| Kafka недоступна после commit job | Outbox сохраняет запуск до восстановления; timeout обрабатывает watchdog |
| Нет данных Premier | Честный статус источника; не подмена данными FACEIT |

Для ревью: проверить ответственность пяти сервисов, схемы взаимодействия и правила идемпотентности. Дальнейшая реализация: OpenAPI/protobuf/JSON Schema, политики доступа, интеграционные и отказные тесты. Подтверждения команды и руководителя в этой версии ещё нет.
