# GA-51 — выбор технологий GameAnalytics

Статус: проект решений для ревью команды. Основание: [ТЗ GA-1](../requirements/mvp.md), [источники GA-2](../research/data-sources.md), [эксперимент GA-3](../research/demo-match-identification.md). ## Критерии выбора

Нужно выполнить FR-01–FR-13: публичные профили, защищённые загрузки, асинхронный анализ, идемпотентность, квоты и хранение. Пять сервисов, Kafka, S3 и Kubernetes приняты командой как границы проекта. Здесь объясняются последствия этого выбора; альтернативы не объявляются непригодными.

Приоритеты: корректность данных и права доступа → опыт команды и достижимость в срок → эксплуатация и стоимость → измеренная производительность. Оценки ниже качественные, применительно к нашей команде. Численные преимущества, облачные цены и SLA не измерялись. Любой вариант требует вычислений, диска, резервных копий и времени сопровождения; open source не означает бесплатную эксплуатацию.

## 1. Серверная платформа

| Вариант | Возможности и надёжность | Опыт, сроки и эксплуатация | Стоимость и производительность |
|---|---|---|---|
| **Go + Gin** | HTTP middleware, валидация; транзакции и авторизацию проектируем сами | У Амира практический опыт Gin/PostgreSQL/JWT, у Ерхана Go; проще разделять задачи и сопровождать | Основной расход — инфраструктура и работа команды. Производительность полного конвейера нужно замерить, скорость HTTP не доказывает скорость парсинга |
| Python + FastAPI | Типизированные API и OpenAPI, удобная связь с Python ML | Хорош для сервиса анализа; перенос всего backend потребует повторить Go-практики команды в Python | Удобная разработка; CPU-парсинг/ML выносятся в отдельные процессы, стоимость проверяется замерами |
| Java + Spring Boot | Готовая инфраструктура приложений, health/metrics, широкий стек | Увеличивает объём освоения основного backend; Java-парсер допустим внутри обработки данных | Память, старт и пропускную способность измерять на нашем сервисе; не считать Java заведомо медленнее |

**ADR-01.** Go/Gin для пользователей, матчей и статистики; Python для анализа. Внутренние синхронные вызовы — gRPC, наружу — REST/OpenAPI. Язык парсера выбирается по GA-3 и поддержке формата, а не ради одинакового языка всех сервисов. Цена решения: поддержка нескольких сред и контрактов. Пересмотр — если нужный парсер не поддерживает выбранный runtime; граница сервиса при этом сохраняется.

Источники возможностей: [Gin](https://gin-gonic.com/en/docs/), [FastAPI](https://fastapi.tiangolo.com/), [Spring Boot](https://docs.spring.io/spring-boot/index.html).

## 2. Основная база данных

| Вариант | Целостность и модель | Опыт и эксплуатация | Сроки, стоимость, производительность |
|---|---|---|---|
| **PostgreSQL** | Транзакции, ограничения и блокировки подходят для связи задания, резерва квоты и outbox | Команда уже работала с PostgreSQL; pgx и миграции знакомы | Меньше обучения; нужны индексы, резервирование и замеры запросов на своих данных |
| MySQL / InnoDB | Транзакционная реляционная модель также подходит | Возможный вариант, но смена драйверов и практик команды без доказанной выгоды | Сопоставимые виды затрат; победителя по скорости без эксперимента нет |
| MongoDB | Документная модель и многодокументные транзакции; отсутствие транзакций не является аргументом против | Удобна для переменных документов, но квоты, связи и ограничения придётся проектировать отдельно | Дополнительная сложность при транзакциях и согласовании схем; не выбираем только ради гибкого JSON |

**ADR-02.** PostgreSQL — источник истины. В MVP один экземпляр допустим, но у каждого сервиса отдельная база/схема и роль; прямые межсервисные записи и SQL JOIN запрещены. Резерв квоты и создание задания принадлежат одному сервису и одной транзакции. Redis — восстанавливаемый кэш и rate limit, не источник баланса квоты. Цена: отказ общего экземпляра затрагивает все сервисы; HA не заявляется без испытаний. Пересмотр — по результатам профилирования и восстановления из backup.

Источники: [PostgreSQL: isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [InnoDB](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html), [MongoDB transactions](https://www.mongodb.com/docs/manual/core/transactions/).

## 3. Событийное взаимодействие

| Вариант | Доставка, хранение и повторное чтение | Эксплуатация и опыт | Применимость и цена |
|---|---|---|---|
| **Kafka** | Журнал, retention, независимые consumer groups; порядок внутри partition | Новая операционная нагрузка: диски, lag, partitions, ACL, восстановление; разворачивает Амир | Удобно отдельно пересчитывать статистику и анализ. Диск/репликация дороже простой очереди; для малого MVP может быть избыточна |
| NATS JetStream | Сохранение и повторное чтение доступны; не путать с Core NATS без durable-хранения | У Амира опыт NATS, но режим JetStream и его отказные сценарии всё равно требуют проверки | Реальная альтернатива Kafka для этого объёма; не отвергается из-за якобы отсутствия replay |
| RabbitMQ: очереди / Streams | Очереди удобны для заданий; Streams дают сохраняемый журнал и повторное чтение | Нужно выбрать модель очередей или Streams и проверить клиентов Go/Python | Также решает задачу; нельзя утверждать, что весь RabbitMQ удаляет данные после первого чтения |

**ADR-03.** Оставляем Kafka по согласованному стеку и потребности в независимых потребителях результатов парсинга. Доставка проектируется at-least-once: транзакционный outbox, consumer inbox и уникальные бизнес-ключи. Kafka сама не обеспечивает exactly-once для PostgreSQL/S3. В Kafka передаются метаданные и ссылки на объекты, а не демки и массивы всех игровых событий. Повторное чтение не создаёт повторного списания квоты.

Стартовый стенд может иметь один broker, но он не отказоустойчив. До эксплуатационного релиза нужны обоснованные retention, объём диска, репликация, права, мониторинг lag и проверка восстановления. Повторный анализ требует ещё существующего исходника/промежуточного набора: retention Kafka не продлевает хранение демки. Пересмотр решения — если эксплуатационные затраты мешают срокам; только отдельным согласованным ADR, не молчаливой заменой Kafka.

Источники: [Kafka concepts](https://kafka.apache.org/41/getting-started/introduction/) (концепции, не закрепление версии), [JetStream](https://docs.nats.io/concepts/jetstream), [RabbitMQ Streams](https://www.rabbitmq.com/docs/streams).

## 4. Файловое хранилище

| Вариант | Надёжность и доступ | Эксплуатация, стоимость и сроки |
|---|---|---|
| **Самостоятельное S3-совместимое хранилище** | Приватные buckets, отдельные роли; checksum, lifecycle и политики проверяем у конкретной реализации | Соответствует желанию Амира разворачивать хранилище и его опыту MinIO; команда отвечает за диски, backup и обновления |
| Управляемое S3 | Снимает часть обслуживания дисков; доступ всё равно проектирует команда | Оплата хранения, запросов и трафика; тарифы надо считать для выбранного провайдера, бюджет пока не согласован |
| Каталог на диске сервиса | Прост для локального опыта | Привязка к узлу и сложности масштабирования/резервирования; не подходит как общий контракт между репликами |

**ADR-04.** Выбираем S3-совместимый API и самостоятельное развёртывание; конкретный продукт/версию фиксируем после проверки лицензии, доступности, lifecycle и восстановления. Не обещаем, что любая S3-совместимая система поддерживает все функции AWS. Файлы приватные; исходник доступен 30 суток после успешной загрузки, далее приложение немедленно запрещает доступ, удаление контролируется фоновым процессом в пределах 24 часов. Отчёт хранится отдельно. Амир отвечает за настройку хранилища, Ерхан — за общую платформу и наблюдаемость.

Оценка диска: `успешные загрузки в сутки × средний размер × 30 × коэффициент репликации` плюс временные файлы, промежуточные данные, отчёты и запас. Например, 10 × 0,3 GiB × 30 = 90 GiB исходников без реплик. Это сценарий планирования, не прогноз спроса. [AWS lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html) используется как справка по концепции; физическое удаление не считается мгновенным.

## 5. Оркестрация и границы ответственности

| Вариант | Преимущества для проекта | Ограничения |
|---|---|---|
| Docker Compose | Быстрый локальный запуск и интеграционные проверки | Не заменяет целевую оркестрацию и испытания восстановления |
| **Kubernetes** | Общие deployment-процедуры, probes, resource limits и изоляция workers | Дополнительная сложность сети, storage и секретов; один узел не обеспечивает HA |
| Управляемая контейнерная платформа | Часть обслуживания у провайдера | Бюджет и ограничения провайдера неизвестны; не соответствует принятой задаче по Kubernetes без согласования |

**ADR-05.** Compose для разработки, Kubernetes для целевого стенда. Развёртывание кластера, CI/CD, метрики/логи и общая инфраструктура — Ерхан; Kafka и S3 — Амир с согласованными manifests, ресурсами и правилами backup; frontend и ML — Қажмұрат. Gateway и инфраструктура не добавляют шестой бизнес-сервис. [Возможности Kubernetes](https://kubernetes.io/docs/concepts/overview/).

## Проверка решений после первой сдачи

- Восстановить данные из backup и пережить перезапуск consumer без дубля задания/квоты.
- Измерить задержку и ресурсы полного конвейера, а не переносить время userinfo из GA-3 на весь ML.
- Проверить недоступность чужого/просроченного объекта и очистку временных файлов.
- Установить версии, retention, ресурсы и лимиты по эксперименту; предварительные бюджеты из GA-1 не выдавать за измеренные максимумы.
- Проверить Premier в GA-58; он остаётся в целевом MVP. Проблема идентификации CS2 решается в реализации GA-21, не требует нового исследования Ерхана для принятия этого документа.

Ревью: подтвердить сравнение и распределение ответственности. Согласование всей команды/руководителя пока не зафиксировано.
