# Требования и план оценки, следующие из обзора литературы

Это предложение для команды: ID и формулировки нужно согласовать и перенести в общий документ требований проекта. Номера в скобках — источники из [sources-table.md](sources-table.md); обоснование — в [review.md](review.md).

## Требования (LR — literature-derived requirements)

| ID | Требование | Основание |
|---|---|---|
| LR-1 | Определить классы «ошибок»: (а) читинг/аномальное поведение, (б) ошибки игрока (неоптимальные решения), (в) визуальные глитчи. Для каждого детектора указывать, к какому классу он относится. Класс (в) вне MVP. | [2], [3], [5], [7], [9] |
| LR-2 | Единая схема данных (тик / событие / раунд / матч / игрок) для CS2 и Dota 2; версия игры и патча хранится вместе с матчем. | [6], [2], [12] |
| LR-3 | Модели по играм отдельные; заявлений об универсальной кросс-игровой модели не делать. Кросс-игровость — на уровне схемы данных, пайплайна и интерфейса. | [3], [10] |
| LR-4 | Идентификаторы игроков анонимизируются во всех сохраняемых и публикуемых наборах данных. | [2] |
| LR-5 | Метки не берутся только из бан-статуса: нужна экспертная выборка и оценка точности и полноты меток. | [2], [3] |
| LR-6 | Выход детектора — оценка подозрительности и доказательства (временное окно, позиции, события), а не вердикт. Решение остаётся за человеком. | [2], [3] |
| LR-7 | Решение о подозрительности игрока опирается на несколько событий, а не на одно. | [2] |
| LR-8 | Пространственно-временные признаки привязываются к карте и окну; фиксируются размер окна и частота (для CS2 — тики). | [2], [3], [6] |
| LR-9 | Объяснение состоит из доказательств (окно, события) и вторичного слоя атрибуции признаков (SHAP или аналог). | [12], [13], [15] |
| LR-10 | Проверить совместимость парсеров (awpy, demoparser2) с форматом CS2 и Dota 2 до начала разработки моделей. | [2], [3], [6] |

## План оценки (EP — evaluation plan)

| ID | Что делаем | Основание |
|---|---|---|
| EP-1 | Разбиение групповое: по матчам, а где возможно — по игрокам и по времени/патчам; не по тикам или окнам. Аугментация только в обучающей выборке. | [2], [17], [18] |
| EP-2 | Метрики: precision, recall, F1, PR AUC, ROC AUC, доля ложных срабатываний в рабочей точке; для вероятностей — калибровка. Accuracy одна не используется. | [2], [3], [8] |
| EP-3 | Временная проверка: обучение на ранних данных, тест на поздних; фиксируем падение качества между патчами. | [3], [12], [17] |
| EP-4 | Для каждого эксперимента заполняется чек-лист утечек (по [17]): зависимость train/test, временная утечка, нелегитимные признаки, предобработка. | [17] |
| EP-5 | Аудит меток: ручная проверка выборки ложных срабатываний и отчёт о доле, оказавшейся ошибками разметки. | [2], [3] |
| EP-6 | Baseline: простые правила/пороги, логистическая регрессия и градиентный бустинг — раньше глубоких моделей. | [17] |
| EP-7 | Объяснения оцениваются двумя способами: согласие прокси-модели (fidelity) и небольшой пользовательский тест (точность и время ответа). Полезность объяснений считается гипотезой. | [13], [14] |
| EP-8 | Обсуждение устойчивости к «умным» читам и дрейфу; результаты формулируются как относящиеся к конкретному периоду. | [3], [4] |
| EP-9 | Результаты по CS2 и Dota 2 отчитываются отдельно, без усреднения. | [10], [12] |
| EP-10 | Сравнение с литературой — только при одинаковых данных, задаче и моменте прогноза; иначе приводим цифры как справочные. | [8], [11], [12] |
| EP-11 | Воспроизводимость: фиксированные seed, версия данных и кода в репозитории. | [2] |
