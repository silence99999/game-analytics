## Проблема и пользователи

Игроку, участвующему в CS2 и Dota 2, нужен единый способ находить доступную статистику, видеть динамику и разбирать конкретные эпизоды собственных матчей. Сводные показатели сами по себе не объясняют, какое действие привело к неблагоприятному результату. Проект исследует возможность дополнить статистику объяснимыми сигналами о потенциальных ошибках.

Целевые пользователи — игроки, тренеры и аналитики любительских и полупрофессиональных команд, киберспортивные клубы и вузовские лиги. Проверка востребованности и формулировок сценариев планируется в GA-49; интервью пока не считаются проведёнными. Сравнение с существующими продуктами выполняется в GA-50, поэтому превосходство над ними здесь не утверждается.

## Цель и измеримые задачи

Цель — разработать и проверить прототип платформы для публичной статистики CS2/Dota 2 и персонального анализа собственных записей с объяснением найденных эпизодов.

1. Проверить источники обеих игр: составить матрицу доступов и полей, сохранить реальные ответы и явно определить ограничения истории.
2. Спроектировать ровно пять прикладных сервисов, контракты API и событий, права доступа и владельцев данных.
3. Реализовать просмотр профиля и доступных матчей другого игрока без обязательной регистрации, с указанием источника и полноты данных.
4. Реализовать загрузку из выбранной карточки, проверку владельца и соответствия матча, асинхронный анализ и отчёт. Приёмка включает правильную запись, чужую запись, другую игру/матч, повреждённый файл и повторную отправку.
5. Для согласованного перечня типов ошибок создать размеченную выборку, baseline и модель; измерить precision, recall и F1 на отложенной выборке без пересечения матчей между обучением и тестом. Размер выборки, перечень ошибок и целевые значения фиксируются после исследования GA-4/GA-52; достигнутые показатели пока отсутствуют.
6. Проверить ограничения ресурсов, повторную доставку событий и восстановление заданий; подготовить воспроизводимое развёртывание, тесты и документацию.

## Обязательный целевой MVP

- Единый профиль с раздельными показателями CS2 и Dota 2, публичный просмотр доступных данных любого найденного игрока. Приватные данные и полная история всех игроков не обещаются.
- История и карточки матчей из подтверждённых интеграций. FACEIT для CS2 и OpenDota для Dota 2 проверены на примерах в GA-2; Premier также обязателен, его практическая проверка вынесена в GA-58.
- Подтверждение Steam-аккаунта для персонального анализа.
- Ручная загрузка записи только из существующей карточки своего матча; рядом инструкция и переход к источнику, где пользователь может получить запись. Отдельной кнопки «Добавить матч» нет.
- Проверка участия и соответствия записи карточке. Неоднозначную запись нельзя принимать как подтверждённый матч.
- Очередь обработки, видимые статусы, структурированная статистика и объяснимые эпизоды потенциальных ошибок. Вывод модели не трактуется как безусловная оценка игрока.
- Бесплатный лимит в три успешных анализа за согласованный период и демонстрационный Premium без лимита числа анализов за период, но с ограничениями ресурсов. Период и технические пределы пока предлагаются в GA-1, а не считаются согласованными. Реальные платежи не входят.

**Условие реализуемости:** GA-3 должна подтвердить надёжную связь записи с карточкой и участником для каждого поддержанного источника. Пока это не доказано, поддержка анализа для источника условна. Если проверка провалится, команда согласует с руководителем сокращение охвата; молча ослаблять проверку нельзя.

По решению пользователя от 19.10.2026 Premier обязателен в MVP. Исследование пути получения карточек оформлено в GA-2; практическая проверка перенесена в GA-58 после первой сдачи 24 октября, точный срок ещё не согласован; полная история любого игрока по одному SteamID не подтверждена. Предполагаемый путь подключения истории через game authentication code и свежий share code требует реального прогона и проверки метаданных матча. Отсутствие карточки означает отсутствие загрузки, а не создание матча через обходной экран. Неподтверждённая интеграция — риск реализации обязательного требования, а не согласованное исключение Premier.

## Архитектура и технологии

| № | Прикладной сервис | Назначение |
|---|---|---|
| 1 | Users / Profiles | Учётная запись, подтверждённые игровые идентификаторы, профиль, тариф и права |
| 2 | Matches / Uploads | Импорт карточек, метаданные файлов, создание задания, проверка и резервирование квоты |
| 3 | Data Processing | Безопасный разбор записей, извлечение событий и идентификаторов, подготовка признаков |
| 4 | Statistics | Агрегация игровых показателей, история и динамика |
| 5 | Mistake Analysis | Версионированный baseline/ML, эпизоды, оценка уверенности и объяснения |

API gateway, frontend, PostgreSQL, Redis, Kafka и S3 — компоненты системы, но не дополнительные прикладные микросервисы. Уведомление о готовности реализуется через статус задания; отдельный шестой сервис не требуется.

Backend: Go, Gin, gRPC, PostgreSQL (pgx, golang-migrate), Redis, Kafka, S3-совместимое хранилище, Swagger/OpenAPI, testify. ML: Python и FastAPI; выбор моделей по экспериментам. Инфраструктура: Docker, Kubernetes, CI/CD и наблюдаемость. Конкретный frontend-стек уточняет его ответственный; это не блокирует описание сценариев.

Записи хранятся в закрытом объектном хранилище ограниченное время, результаты и метаданные — в PostgreSQL. Kafka передаёт идентификаторы и события, а не большие бинарные файлы. Повторная доставка не должна создавать дубликаты результатов или повторное списание квоты. Каждый сервис владеет своими данными; конкретное физическое размещение баз фиксируется архитектурным решением.

## Сложность, ограничения и проверка

Инженерная сложность: изменяемые бинарные форматы записей, ограниченная доступность внешних данных, сопоставление идентификаторов, обработка больших файлов, асинхронные отказы, согласование схем событий и объяснимость ML.

Метод исследования: сравнение источников и альтернатив, прототипирование парсинга, ручная разметка по инструкции, контроль утечки данных, сравнение модели с простым baseline и проверка основных пользовательских сценариев. Для эпизодов требуется правило совпадения по времени/интервалу, которое закрепляется до расчёта метрик. Метрики двух игр отчётно разделяются.

Нагрузка и точность пока не измерены. Целевые нефункциональные требования — отдельные проверяемые гипотезы в GA-1, подлежащие согласованию с возможностями стенда. При недоступности источника интерфейс показывает причину и дату последнего обновления. Отсутствие данных не интерпретируется как нулевой результат игрока.

## Дальнейшие этапы

1. Подтвердить источники и соответствие записей, согласовать границы и требования.
2. Реализовать вертикальный сценарий: вход → карточка → загрузка → обработка → отчёт сначала на одной игре, затем на второй.
3. Подготовить выборку, baseline и оценку; подключить ML к уже работающему сценарию.
4. Проверить отказы, доступы, лимиты и нагрузку; завершить Kubernetes-развёртывание и документацию.
5. Провести приёмку по требованиям, зафиксировать фактические результаты и подготовить защиту. Сроки после первой сдачи согласуются отдельно.

Будущие улучшения: автоматическое получение записей при доступном разрешении, реальные платежи, расширенные командные функции и новые игры. Premier относится к обязательному MVP, но его техническая проверка пока не завершена.
